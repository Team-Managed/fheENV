# Smart Contract

`fheENVRegistry.sol` is the implementation behind an ERC-1967 UUPS proxy on Ethereum Sepolia. It
stores project authorization, encrypted environment metadata, and CoFHE `euint128` AES-key handles.

**Current proxy:**
[`0xb9a29d0Cfb402d91c6f70eF117758C118f00F5B2`](https://sepolia.etherscan.io/address/0xb9a29d0Cfb402d91c6f70eF117758C118f00F5B2)

## Roles

| Role                  | Authority                                                    |
| --------------------- | ------------------------------------------------------------ |
| Proxy owner           | Authorize UUPS implementation upgrades                       |
| Project primary owner | Manage project, remove co-owners, transfer primary ownership |
| Project co-owner      | Update environments and grant/revoke members                 |
| Member                | Decrypt current environment handles when permitted           |

The proxy owner must be a Safe or equivalent multisig in production, preferably behind a timelock.
It is separate from per-project ownership.

## Project management

| Function                                | Access        | Purpose                                        |
| --------------------------------------- | ------------- | ---------------------------------------------- |
| `createProject(name)`                   | Anyone        | Create a project; caller becomes primary owner |
| `addOwner(projectId, address)`          | Project owner | Add a co-owner                                 |
| `removeOwner(projectId, address)`       | Primary owner | Remove a co-owner                              |
| `transferOwnership(projectId, address)` | Primary owner | Replace primary owner and revoke caller        |

The primary owner cannot remove itself with `removeOwner`; it must transfer ownership.

## Environment and access

| Function                 | Access        | Purpose                                                    |
| ------------------------ | ------------- | ---------------------------------------------------------- |
| `updateEnvironment(...)` | Project owner | Validate optimistic version, store new FHE handles and CID |
| `getEnvironment(...)`    | Anyone        | Read ciphertext handles, CID, version, timestamp           |
| `grantAccess(...)`       | Project owner | Permit one member on current handles                       |
| `batchGrantAccess(...)`  | Project owner | Permit up to 100 members                                   |
| `revokeAccess(...)`      | Project owner | Mark member inactive and emit revocation                   |
| `hasAccess(...)`         | Anyone        | Read membership state                                      |

`revokeAccess` cannot revoke a CoFHE permission already attached to the current handles. The CLI
rotates the AES key and handles by default after removal.

## Upgrade safety

The implementation disables direct initialization. `initialize(initialOwner)` runs once through the
proxy. `_authorizeUpgrade` is guarded by OpenZeppelin `onlyOwner`. Every upgrade must:

1. preserve and validate storage layout;
2. deploy and verify the new implementation;
3. pass contract, upgrade, and CLI compatibility tests;
4. receive multisig/timelock approval;
5. execute `upgradeToAndCall` through the proxy;
6. verify implementation slot, owner, state, events, and application reads;
7. retain proposal, reviews, simulation, transaction, and validation evidence.

## Security properties

- Optimistic locking rejects concurrent environment overwrites.
- Inputs validate project names, addresses, CIDs, and batch limits.
- State updates precede FHE permission interactions.
- Only FHE handles and encrypted blobs are public; no environment plaintext is written to chain.
- Upgrades are explicit and access-controlled; they are not trustless.

## Deployment boundary

The current deployment is a CoFHE-supported testnet pilot. Testnet tokens, relayers, RPCs, and
protocol services have no production availability or economic guarantees. A mainnet deployment
requires CoFHE mainnet support, independent contract and client audits, multisig/timelock
governance, monitoring, incident drills, supported-chain configuration, and a separately approved
deployment record. Cheaper EVM chains such as Base or Arbitrum are usable only after CoFHE supports
the selected network and all integration tests pass there.
