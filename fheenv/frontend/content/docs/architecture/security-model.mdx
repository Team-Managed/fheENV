# Security Model

<Callout type="warn">
  Report vulnerabilities through GitHub private vulnerability reporting or security@fheenv.com, not
  a public issue.
</Callout>

## Core model

Environment content is encrypted locally with a fresh AES-256-GCM key. Only the encrypted blob
reaches IPFS. The key is split into two FHE ciphertext handles on the supported CoFHE testnet. A
permitted signer obtains a CoFHE permit, decrypts the handles through the threshold network, and
decrypts the blob locally.

## Protected boundaries

| Threat                     | Protection                                                           |
| -------------------------- | -------------------------------------------------------------------- |
| IPFS/gateway disclosure    | AES-256-GCM ciphertext                                               |
| Public chain inspection    | FHE ciphertext handles                                               |
| fheENV service compromise  | No service-side plaintext or signing key                             |
| Credential file disclosure | v2 config stores references only                                     |
| Desktop credential theft   | Native OS credential store                                           |
| Arbitrary KMS signing      | Local chain/contract/selector/value/gas/fee policy                   |
| External process abuse     | Absolute executable, no shell, minimal environment, bounded protocol |

Production signing keys remain in WalletConnect wallets, Ledger secure elements, AWS KMS, or an
external custody system. WalletConnect session state is AES-256-GCM encrypted with a random key held
in the native credential store. The development-only local keyfile is scrypt-derived AES-256-GCM
with mode `0600`.

## Important limits

- A compromised client, wallet, signer provider, or authorized process can expose plaintext it
  legitimately decrypts.
- CoFHE has no `revokeAllow` for an existing handle. `team remove` must rotate to new handles;
  copied old plaintext cannot be recalled.
- Native keyrings depend on an unlocked macOS/Windows user session or a Linux Secret Service/D-Bus
  session. Production fails rather than falling back.
- Local KMS policy reduces accidental misuse but does not contain a fully compromised workload. IAM
  and organization policy are authoritative.
- The external signer executable is part of the trusted computing base.
- Analytics are opt-in and minimal; local audit export is not a durable SOC 2 ledger.
- Current chain support is limited by CoFHE network availability. The product is not represented as
  mainnet-supported until the protocol is available and the deployment is separately audited.

## Authorization

```text
Proxy multisig ──► authorize UUPS implementation upgrades
Primary owner  ──► project operations and co-owner removal
Co-owner       ──► environment updates and member grants/revocations
Member         ──► decrypt current handles when CoFHE permits it
```

The UUPS proxy owner and project owners are distinct roles. Production must place proxy ownership in
a Safe or equivalent multisig, preferably with a timelock. Project primary ownership should also use
organization-controlled signing where practical.

## Data at rest

| Data                  | Location                          | Protection                        |
| --------------------- | --------------------------------- | --------------------------------- |
| Source `.env`         | Operator machine                  | Filesystem and endpoint controls  |
| Encrypted environment | IPFS                              | AES-256-GCM                       |
| AES key handles       | CoFHE-supported chain             | FHE ciphertext                    |
| Credential values     | Native store or selected provider | Provider controls                 |
| WalletConnect state   | Local state file                  | AES-256-GCM; key in native store  |
| Development signer    | `~/.fheenv/wallet.json`           | scrypt + AES-256-GCM, mode `0600` |

## Incident response

Follow the
[credential compromise runbook](https://github.com/Team-Managed/fheENV/blob/main/docs/runbooks/credential-compromise.md)
and
[signer rotation runbook](https://github.com/Team-Managed/fheENV/blob/main/docs/runbooks/signer-rotation.md).
Rotation must capture detection, containment, authorization updates, validation, revocation, and
durable evidence.
